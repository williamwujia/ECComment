# 变更管理流程

目标是让任何人隔一段时间回来，都能在几分钟内回答：现在做到哪里、最近改了什么、为什么这么改、下一步是什么。

## 一次变更的闭环

1. **开始**：读 `PROJECT_STATUS.md`、`CHANGELOG.md` 的未发布部分和相关决策；检查工作区是否已有改动。
2. **实施**：代码与测试一起修改。发现范围外问题时，写入状态页，不在本次顺手扩张范围。
3. **记录**：把使用者可感知变化写入变更记录；把长期取舍写入决策记录；把未完成项写入状态页。
4. **验证**：运行相关测试、`git diff --check`，复核 `git diff` 和未跟踪文件。
5. **提交**：一个提交表达一个完整意图，提交信息优先说明结果，例如 `feat: remind stale SKU updates`。
6. **发布**：把 `[未发布]` 移到日期标题下，再建立新的空 `[未发布]` 区域。

## 不同信息应该写在哪里

| 信息 | 位置 | 示例 |
| --- | --- | --- |
| 系统现在支持什么 | `PROJECT_STATUS.md` | 支持快照回退 |
| 正在做但未完成什么 | `PROJECT_STATUS.md` | SKU 提醒尚未完整测试 |
| 某次增加/修复了什么 | `CHANGELOG.md` | 新增京东 CSV 导入 |
| 为什么选择某种方案 | `docs/DECISIONS.md` | 为什么拆分三层记录 |
| 具体实现细节 | 代码、测试、提交 | 边界条件和函数行为 |
| 操作使用方法 | `README.md` 或专题说明 | 如何启动、导入、回退 |

## 完成定义（Definition of Done）

一项修改只有同时满足以下条件才算完成：

- 行为达到目标且没有夹带无关改动；
- 新行为或缺陷修复有对应测试；
- 相关测试通过，未验证项明确写出；
- `[未发布]` 已记录使用者可感知变化；
- 状态页与实际工作区一致；
- 新的长期取舍已记录；
- 工作区没有意外临时文件。

## 每周五分钟维护

- 清理已经完成但仍留在“进行中”的项目。
- 检查未发布记录是否能对应到实际提交。
- 将超过一周仍未处理的口头待办写入状态页或删除。
- 检查决策是否已被代码悄悄改变；如有变化，补一条替代决策。
